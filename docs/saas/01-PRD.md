# Medusa 电商 SaaS PRD

状态：原始 PRD 草案，第一阶段实际交付见 M0–M6 实施与验收报告；第二阶段尚未实施。原草案依据仓库 HEAD `340da77f722a5a53c48bf35276f96ec261a65736`，后续实施已冻结独立 MIT 基线。第一阶段MVP仅为原生Medusa的SaaS改造；模块管理、AI运营、Helpdesk/电商CRM/营销产品层/完整行为统计及新增底座全部第二阶段。详见[第二阶段总计划](23-PHASE2-DEVELOPMENT-PLAN.md)、[AI规格](04-AI-NATIVE-OPERATIONS.md)与[第二阶段客户运营](06-CUSTOMER-OPERATIONS-FOUNDATION.md)。

## 1. 目标与产品定位

以许可允许的 Medusa 核心为交易引擎，开发共享应用实例、共享 PostgreSQL 数据库、以 `tenant_id` 隔离商户的电商 SaaS。商户注册后可以创建一个独立品牌商城，管理商品与订单，独立配置支付并完成销售。平台负责租户生命周期、套餐、配额和运维。第二阶段再增加智能运营入口：经营目标驱动诊断、行动、审批执行和效果复盘；第一阶段沿用原生电商后台操作。

这是商户独立站平台，不是集中买家流量的多卖家 Marketplace。第一版每个租户一个商城；销售渠道不等于租户。后续可扩展租户内多渠道和多店，但不改变租户边界。

## 2. 默认范围与假设

- 使用 TypeScript，保持 Medusa 模块结构；接受维护一个有明确补丁清单的核心 fork。
- 共享数据库与进程、独立租户数据；首版不混用独立实例方案。
- 首版单币种、单销售地区、单仓库、固定运费和可配置税率。基础设施设计允许以后扩展。
- 支付首选单一渠道。规划以商户自有 Stripe 账户、商户直接收款为参考实现；平台不代收、不做分账。目标地区不能使用 Stripe 时先重估支付范围。
- 商户订单收款与平台 SaaS 订阅收费是两套业务，凭据和回调不得混用。
- 固定主题、配置式装修，不开发拖拽页面编辑器。
- MVP 仅店主；正式 V1 独立实现店主/运营/仓库/客服固定角色。不复用受商业许可约束的 Medusa RBAC/SSO。
- 采用托管对象存储、邮件和支付服务。供应商账户、上线域名和真实支付授权需要负责人提供。
- 首版从空库或可明确归属的开发库开始；未知生产数据的批量迁移不在默认范围。
- 第二阶段增加全部AI运营、Helpdesk、客服角色/SLA、电商CRM、单邮件营销旅程和完整行为统计；相关身份、会话、同意与客户时间线底座也在第二阶段实施。MVP不包含本次扩展，不做全渠道客服或销售商机CRM。

## 3. 授权边界：实施前置条件

当前仓库是 open-core，不能把整个 checkout 视为 MIT。`ENTERPRISE-LICENSE.md` 将 RBAC、SSO 及指定类型、政策、界面和测试路径列为企业材料；编译后的产物也适用。

上线前必须：

1. 确定可合法使用的版本/commit，锁定依赖和来源。
2. 根据完整路径清单检查源码、导入、包依赖与构建输出；仅关闭 feature flag 不作为完成条件。
3. 保留许可通知与第三方依赖清单，生成 SBOM。
4. 对选择的 MIT 源码独立开发租户成员授权；不复制企业实现，不绕过许可验证。
5. 如当前构建不能在许可允许范围内工作，选择核实过的早期 MIT 基线或取得授权。更换基线可能改变后续工时。

验收物：版本决策记录、许可矩阵、可重复构建结果、产物检查报告。任何源码历史的授权判断须有证据，不能只因版本较早就推定为 MIT。

## 4. 用户与权限

| 身份 | 可操作范围 |
|---|---|
| 平台运营人员 | 开通、暂停、套餐、配额和平台状态；默认无权浏览商户客户和订单 |
| 店主 | 本租户商品、订单、成员、支付配置、商城配置 |
| 运营人员（V1） | 本租户商品、客户、订单操作；无成员和支付密钥权限 |
| 仓库人员（V1） | 本租户库存、发货信息；不读取支付配置及非必要客户字段 |
| 客服人员（V1） | 本租户分配/授权工单、必要客户/订单字段；不能读取支付密钥、无默认退款权限 |
| 消费者 | 当前商城浏览、购物车、自身订单与账户 |
| 后台任务/应用 | 服务身份绑定明确租户和用途，不拥有默认跨租户权限 |

平台确需排障访问商户数据时，使用单独授权的支持会话，记录理由、操作者、租户、时限和访问操作。普通管理员令牌不能隐式变成全库读取权限。

## 6. 关键用户流程

### 6.1 商户开店

邮箱验证 → 创建租户 → 创建成员绑定 → 分配子域名 → 初始化 Store、Region、Currency、Sales Channel、仓库和配置 → 租户进入 active → 添加商品 → 配置支付 → 试单。

开店以可重试的初始化流程执行，每一步有幂等标识。未完成的租户不对消费者开放结账。

### 6.2 消费者下单

受信域名解析租户 → 查询可售商品 → 创建租户购物车 → 服务端校验商品/价格/库存/运费/税率归属 → 服务端重算金额 → 创建支付会话 → 完成订单 → 处理可信支付回调 → 商家履约。

要明确选择库存预留与支付授权的顺序，复用已验证工作流，并测试超时、失败及补偿。每一阶段都再次检查关联资源归属，不能只在创建 Cart 时校验一次。

### 6.3 暂停、退款与注销

暂停限制商城新结账和商家新增业务，不阻断已发生支付的回调、退款、审计和依法需保留的数据。恢复不重复初始化。注销按保留规则导出与清理数据，不能直接级联删除全部支付记录。

## 7. 数据与租户隔离设计

### 7.1 隔离契约

- 任何租户业务操作必须有可信 `TenantContext`，缺失时拒绝；不设置默认租户。
- `tenant_id` 来源于服务端验证过的成员身份、已验证域名或服务身份；请求 body/query/header 中的任意 tenant_id 不具备授权效力。
- 商家访问某租户前验证 membership；消费者 Token 绑定 tenant 和客户；公开商城只返回该租户公开字段。
- 域名映射是租户路由，不是登录授权。只信任可信反向代理提供的 Host；限制可转发头。
- 不在全局变量或共享单例上修改“当前租户”。请求可用 AsyncLocalStorage 辅助传播，但关键写入仍有显式上下文；异步执行必须重新验证。
- 普通业务禁止无租户查询和后台 `bypass`。真正的平台跨租户任务使用独立入口、最小权限和审计。

### 7.2 数据分类

| 分类 | 示例 | 处理 |
|---|---|---|
| 平台控制数据 | tenant、membership、domain、subscription、quota | 独立控制接口；部分天然跨租户，仅平台角色可访问 |
| 租户主数据 | product、customer、order、cart、inventory、store、region、payment | `tenant_id NOT NULL`，所有读取/写入/删除受限制 |
| 子记录与关联 | variant、address、order_item、capture、refund、product_sales_channel 等 | 原则上增加 tenant_id；特殊例外须有约束和审计证据 |
| 公共只读字典 | 核实后的 ISO 币种/国家等 | 允许共享，但租户不能修改公共定义；店铺启用配置属租户 |
| 流程/任务状态 | workflow execution、event、job、retry、idempotency | tenant 写入持久化元数据，恢复和补偿时复原上下文 |

必须生成逐表、逐接口覆盖矩阵。模型存在 `store_id` 或销售渠道关联不能替代这份矩阵。

### 7.3 数据库约束

- 索引优先围绕 `(tenant_id, 常用过滤字段)`；按真实查询计划优化，避免给所有列盲目加索引。
- 检查所有业务唯一约束。商品 handle、客户邮箱/账号等改为租户内唯一，保留软删除条件；token 等安全凭据仍可全局唯一。
- 同库且适合约束的关联使用复合外键确保父子 tenant 一致，父表配套唯一约束。
- Medusa 跨模块 Link/Joiner 不一定有常规数据库外键；链接创建、查询展开和目标服务必须共同验证归属。不能承诺单靠复合外键覆盖全系统。
- PostgreSQL RLS 作为第二道防线：租户表启用策略，应用角色无 BYPASSRLS，按需 FORCE RLS。通过事务局部设置可信上下文。
- RLS 必须验证 ORM、连接池、嵌套事务、读请求、raw SQL 和 worker 的兼容性。SET LOCAL 只能在对应事务内有效，禁止用会残留在连接上的 session 设置。
- 数据迁移账号与应用账号分离。自动化检查应用不能绕过 RLS。

### 7.4 数据库之外

- 缓存键、锁、幂等键、搜索文档/过滤和导出任务都包含租户边界。
- 对象存储按租户命名空间并校验访问；仅目录前缀不构成授权。私有文件使用有限期签名访问。
- 支付密钥使用受控秘密存储或加密存储，普通查询/日志不返回明文；共享 Provider 初始化时不能覆盖另一租户配置。
- 回调以验证后的 Provider 账户/绑定解析租户，并核对交易归属；不能信任 URL 参数直接选租户。
- 队列载荷保存 tenant、用途、追踪 ID；拒绝缺失上下文的重试任务。事件发布和数据库提交的一致性通过 outbox 或等效机制保障。
- 邮件、Webhook 订阅及通知收件人必须属于任务租户。

## 8. 非功能需求与上线门槛

- 隔离：两个租户完整负向测试通过，无跨租户读写、关联、任务、文件和凭据访问。
- 正确性：重复结账/支付回调/退款请求可安全重试；不存在重复扣款、重复履约或错误库存补偿。
- 参考性能验收：8 核/32GB、10 个测试租户、每店 1,000 商品/2,000 变体/10,000 历史订单；20 RPS 持续 30 分钟（80% 浏览、15%购物车、5%订单相关操作），另做 20 并发结账冲突测试。外部支付使用沙箱，支付耗时单列。该配置是测试目标，不是容量承诺。
- 参考目标：普通 API P95 ≤800ms、API 5xx <1%；结账单独统计且排除外部支付等待；测试期间无资源持续增长、库存越界或队列不收敛。不达标须调整配置、优化或降低承载目标。
- 备份：首版异机全库备份及恢复演练，建议 RPO≤24h、RTO≤4h，取决于数据规模；V1 按业务要求接 PITR 并验证。
- 安全：密钥不进入日志，错误不泄露其他租户实体存在性；限制登录和结账速率；审计支付、权限、库存和租户生命周期操作。
- 可维护性：锁定版本、维护 fork 补丁清单、CI 隔离测试；至少演练一次补丁重建和回滚。
- 上线前独立审查关键租户、支付和权限路径；审查排期与供应商等待不算 Codex 运行时间。

## 9. 第二阶段：AI 原生业务驱动

运营首页以经营目标和行动队列为入口，自然语言作为辅助交互。目标、指标定义、证据快照、行动方案、审批、工具执行、效果观察和模型费用均是可追踪的租户业务对象。

业务分析使用确定性指标和规则；AI 负责解释、计划与内容。工具通过可信 TenantContext 调用 Medusa 工作流，不直接操作数据库。审批绑定实际差异、对象版本和有效期，执行前重新授权和验证数据。

第二阶段先提供日报/异常、商品草稿和批准后的内容更新，再增加价格促销、客户生命周期、库存售后建议和目标实验优化。第一阶段不交付AI功能或专用AI底座。自动执行默认关闭，仅在商户事先明确授权的动作、频率、商品范围及预算内运行。

数据、向量检索、历史、任务、缓存和日志都遵守租户隔离；原始个人信息尽量不发送模型。模型故障不得阻塞结账，缺成本或样本时不输出虚假利润或可靠预测。

详细流程、场景、60/150案例评估、费用控制以[AI规格](04-AI-NATIVE-OPERATIONS.md)为准。新增Helpdesk/CRM/营销/分析的公共底座、范围和工时全部进入[第二阶段](06-CUSTOMER-OPERATIONS-FOUNDATION.md)，不阻塞MVP。MVP仅保留原生交易事件、客户账户、租户授权及必要业务任务；不提前实施新增埋点/分析、AI工具/审批、模型运行和其他新域。

## 10. 暂不包含

完整会计总账、应收应付、采购/MRP、平台代收与分账、Marketplace、多主题市场、拖拽建站、插件市场、SSO、细粒度动态 RBAC、全球税务自动申报、未知来源生产数据库的迁移。AI 不包含广告账户自动投放、自动退款/转账、供应商自动采购、无边界全自动经营或跨租户数据训练。
