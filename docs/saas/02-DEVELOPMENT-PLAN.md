## 1. 估算口径

Codex 会话工时指主动开发会话的墙钟时间，包括阅读、编码、执行构建、测试、诊断与修复；不等于人工工时、模型推理时间、token 数或 API 费用。不包含供应商审核、负责人等待、长时间无人值守试运营和独立审查排队。

假设：需求按 PRD 固定；核心 fork 可接受；权限为简单角色；一种商户支付渠道；一套主题；无未知生产数据迁移。工时是规划判断，没有完成全仓审计或实施基准测试。

| 范围 | Codex 基础工时 | 含额外约 25% 预算余量 | 人工决策/验收投入参考 |
|---|---:|---:|---:|
| 完整基础租户隔离（下述 W0–W2 与 W6 中的隔离部分，其他阶段相关隔离联调也计入） | 120–240h | 150–300h | 20–40h |
| **第一阶段MVP：原生Medusa SaaS改造（W0–W6）** | **360–600h** | **450–750h** | **40–80h** |
| 第二阶段增量：模块管理＋电商增强＋全部AI＋客户运营 | 1,668–2,848h | 2,085–3,560h | 148–276h |
| **完整 V1 从零预算（含AI、Helpdesk/电商CRM/营销/行为统计）** | **2,028–3,448h** | **2,535–4,310h** | **188–356h** |

基础隔离已经包含在 MVP 估算中，不能额外加 120–240h。V1 包含新版 MVP，不能再加一次 MVP；完整AI工时包含第二阶段AI起步切片。旧版 E5 基础助手被替换，不再计费。单项区间包括通常的联调修复，额外预算余量用于更大返工、Provider 差异、MIT 基线变化等，不是再次预订同一测试工作。

此前 300–600h 是较轻范围/独立实例首版的粗估；本计划明确采用共享数据库并加入 RLS、Link 查询、异步恢复和完整负向测试，故使用新的分解估算。达到估算上限仍未完成时，必须依据剩余任务重估，不用删掉隔离验证来宣称按期交付。

## 2. 代码与系统边界

建议实施布局（路径为计划，不是已有文件）：

- `packages/modules/tenant`：租户、成员、域名与服务层。
- 独立 tenancy 基础包：TenantContext、查询/写入守卫、任务封装、测试工具；具体位置在 W0 架构评审决定。
- Medusa 受许可允许的模块补丁：业务模型、仓储、Link/Query、工作流上下文和约束迁移。
- 店铺配置、配额、SaaS 订阅模块；模块间通过明确接口连接。
- 平台管理界面、商家界面和固定商城前端。后台复用前须通过 MIT 产物检查。
- PostgreSQL、Redis、对象存储、秘密存储；环境区分开发/测试/生产。
- 共享 worker：任务携带 tenant，公平调度和并发限额；不为每个租户常驻一套进程。

HTTP → 身份与租户解析 → 授权 → 工作流/服务 → 仓储/查询 → 事务与 RLS。

旁路（后台任务、回调、导入导出、CLI）必须从受验证的上下文入口进入相同服务约束。前端隐藏按钮不代替后端授权。

## 3. 电商基础 MVP 工作包

### W0 基线、设计与验证环境：24–40h

任务：

1. 锁定 MIT 可用版本与许可矩阵，检查依赖和构建产物；生成 SBOM。
2. 部署 PostgreSQL/Redis，建立真实数据库测试环境，跑基础 HTTP 和交易用例。
3. 审计模型、唯一索引、Link 表、raw SQL、Graph/Index Query、工作流和后台路由。
4. 形成逐表/逐入口归属矩阵、威胁模型、角色与暂停规则。
5. 商品隔离试点：两个租户，验证模型扩展、仓储守卫及 ORM/RLS 事务路径。

验收：MIT 基线可构建；试点能拒绝越权且连接池不串租户；形成可实施补丁清单。失败则先调整技术路线和工时，不继续大面积加字段。

依赖：无；需要可用数据库和选定版本。

### W1 租户数据与统一上下文：48–80h

任务：

1. tenant/membership/domain/初始化状态与内部平台身份。
2. 平台、租户、公共字典三类数据边界；消费者和商家认证身份独立。
3. 主表、子表、关联表的 tenant 字段及索引；租户内唯一约束和归属一致性。
4. HTTP/服务/CLI/worker 上下文契约，缺失上下文拒绝、平台特权独立通道。
5. RLS 与最小数据库角色；迁移角色分离；事务/连接池/补偿恢复测试。
6. 开店幂等流程、域名归属和租户生命周期。

验收：所有租户表的归属与策略可机器检查；租户 A 无法写入 tenant B；失败开店可恢复；并发 A/B 请求不能复用错误上下文。

依赖：W0。

### W2 完整交易隔离与异步入口：64–104h

任务：

1. 商品、价格、客户、地址、库存、仓库、购物车、订单、税费、运费及配置。
2. 服务 CRUD、批量操作、软删除恢复、列表/count、详情、Graph/Link/Index 关系展开。
3. 校验购物车内商品/价格/优惠/地址/库存全部归属，不能信任已知全局 ID。
4. 工作流 execution/event/retry/补偿保留 tenant；缓存、锁、幂等键、搜索过滤隔离。
5. 回调入口协议和凭据边界；文件访问、邮件收件人、导出任务隔离。
6. 不在 MVP 开放的默认路由显式关闭或守卫，并验证不能通过直接请求绕过界面。

验收：两店使用相同邮箱、handle、购物车幂等键仍互不影响；完整下单隔离；缺 tenant 的事件拒绝；任务重启恢复后仍正确；所有开放入口有覆盖记录。

依赖：W1；Provider 真正动态配置与退款联调在 W4 完成。

### W3 商家后台与消费者商城：80–136h

任务：

1. 店主登录、商品/变体/图片、单仓库存、客户和订单页面。
2. 固定主题：主页、列表、详情、购物车、结账、订单确认/历史；基本移动端体验。
3. 店名/Logo/主题色配置、平台子域名路由和基础 SEO。
4. 服务端数据缓存按 tenant 分区；商城客户令牌绑定 tenant；后台操作与列表同步守卫。
5. 部署店面预览/生产配置，避免客户端持有管理令牌。

验收：两个域名展示各自商品；切换域名不能沿用对方客户会话；页面刷新与错误流程正确；直接请求后台接口仍受限。

依赖：W1、W2 API 契约。可以做静态界面准备，但交易联调不得绕过 W2。

### W4 商户支付与订单履约：56–96h

任务：

1. 一个 Provider 的逐租户安全配置：秘密存储、服务端解析，不共享可变配置对象。
2. 授权/收款/回调、金额重算、重复/乱序事件、重试及事件归属验证。
3. 库存预留、释放、并发结账、失败补偿与订单支付状态一致性。
4. 手动发货、取消、全额/部分退款及失败处理。
5. 基础经营统计；订单金额、收款、退款口径和币种明确。

验收：两家商户分别使用独立沙箱账户，不能串账；重复事件无重复动作；库存冲突正确处理；退款只能使用订单租户的渠道账户。上线前做已授权的真实小额支付/退款验收。

依赖：W2、W3；需要支付沙箱及商户账户。等账户期间可以测试契约，但 mock 测试不能替代最终 Provider 验收。

### W5 平台管理与最低运营保障：40–64h

任务：

1. 平台租户列表、人工试点套餐开通、暂停恢复、商品/上传配额与限流。
2. 暂停后禁新单，保留已付款履约、回调、退款与审计通道。
3. 集中监控、带 tenant 标签的追踪与审计，敏感数据脱敏。
4. 秘密管理、异机备份、全库恢复演练、部署与迁移回滚手册。

验收：普通平台人员不能直接浏览业务数据；配额并发下不超限；备份在另一测试库实际恢复；无密钥日志；健康检查区分 API/DB/worker。

依赖：W1；暂停与支付状态联调依赖 W4。

### W6 验收、安全修复与试点：48–80h

任务：

1. 跨租户攻击矩阵、关键交易 E2E、并发和乱序场景、上下文遗漏扫描。
2. 完成 PRD 定义的 10 租户性能测试，记录数据集、环境、结果和瓶颈。
3. 应用账号 RLS 绕过测试、连接池泄漏测试、共享 Provider 并发测试。
4. 部署演练、恢复演练、fork 升级/重建与回滚演练。
5. 独立审查问题修复、真实支付验收、少量试点商户反馈修复。

验收：没有未解决的跨租户/支付/数据损坏缺陷；所有开放接口被审计；发布清单、问题清单、恢复证据齐全。

依赖：W0–W5；独立审查人员、真实账户与域名由负责人协调。

**第一阶段MVP合计：360–600h，仅W0–W6。** 复用原生Admin和现成参考店面完成租户适配，不定制重写电商系统。

全部AM/A AI工作包、HM/F客户运营工作包转入第二阶段，不增加MVP功能、底座或验收。第一阶段仍需对原生事件、工作流、任务、Provider和所有开放接口完成tenant改造；这些是交易隔离必需工作，不是AI底座。

## 5. 依赖、关键路径与组织

第一阶段关键路径：W0 → W1 → W2 → W4 → W6。W3接口稳定后推进；W5暂停/恢复与W4联调。第一阶段不依赖AI账户、埋点/指标管道、工具网关、AI审批或模型评估。

第二阶段按MVP发布验收与接口稳定后执行 MOD、AM/A、E和HM/F；先落实模块资格、角色、事件指标、客户身份/同意及知识权限，再增加模型/工具/审批与业务场景。模型及营销账户、成本数据和经营样本仅作为第二阶段前置条件；实际发布门槛见 [发布验收](21-RELEASE-ACCEPTANCE.md)。

不假设多个 Codex 会话会线性缩短时间。若未来使用多个开发执行者，先拆分接口与数据库所有权，避免同时修改 schema、上下文与 Provider；共享数据库迁移要串行验收。

单条开发流、每天 8 个有效会话小时、每周 5 天的数学换算：

| 范围 | 基础工作周 | 含预算余量工作周 |
|---|---:|---:|
| 第一阶段原生Medusa SaaS MVP | 9–15 周 | 约12–19周 |
| 第二阶段增量 | 约42–72周 | 约53–89周 |
| 完整 V1（从零开始） | 约 51–87 周 | 约 64–108 周 |

这是时间预算，不是无人值守连续运行承诺；实际日历还受需求反馈、账户、支付审核和试运营影响。人工投入与会话工时有部分重叠，不简单相加为日历工期。

建议每 8–16h 形成可审查增量，每个工作包关闭前更新剩余工时。按实际测试、返工、缺陷和复杂度更新预测；不用代码行数或提交次数判断进度。

## 7. 风险与额外工作

- MIT 基线切换：可能使模型/API/后台版本不同；G0 后重估，不能照搬此处所有具体文件路径。
- 深入共享数据库改造：自动生成仓储、Graph/Link/raw SQL 与 RLS 可能不兼容；试点发现后决定明确补丁，不通过禁用验证来绕过。
- Provider 全局初始化：需改成每次操作安全解析租户配置；共享单例可变密钥会造成串账。
- 未知生产数据：另立迁移项目；tenant 来源必须可验证，不能把所有记录默认归给首个租户。
- 国内支付/多地区：替换参考 Provider 或涉及跨境/分账时另估，不默认包含在一渠道预算中。
- 成本：上述工时不能直接转换 token/API 费用；开发时记录调用消耗，原型后建立真实成本预算。
- 历史部署容量估算基于每租户独立实例；本方案共享实例后不能直接沿用，必须重新压测。
- 第二阶段AI推理费用、模型数据区域、营销订阅、成本字段和经营历史是该阶段前置条件；数据不足时按规则降级，不以生成内容代替真实事实。
- AI 无收益保证，模型升级需要固定案例回归；工具及检索隔离不能仅靠 Prompt。交易队列优先于分析任务。
- 客服来信不是身份凭证；邮件入站、工单可见性、匿名身份及同意是新增验证路径。外部分析全局Token不通过客户端tenant过滤保护。
- 自建Helpdesk默认站内/邮件；若改接现成客服系统需重新估算同步与许可范围，不能直接推定成本更低。
