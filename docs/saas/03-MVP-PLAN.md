# 独立 MVP 计划

## 1. MVP 目标

用 Medusa 许可允许的核心，在共享进程和 PostgreSQL 中通过 tenant_id 隔离商户。面向少量试点商户验证：开店 → 上架 → 浏览 → 下单 → 独立收款 → 发货 → 退款。

MVP 是可试运营、可人工收费的产品，不只是两个租户的演示页面；收费套餐可人工确认开通，自动订阅留给第二阶段。按最新范围决定，AI运营、Helpdesk、CRM、营销产品层、完整行为统计及其新增底座全部第二阶段；MVP只将原生Medusa改造为SaaS，不交付新增智能运营。任何降范围都不降低隔离、支付和恢复验收要求。

## 2. MVP 包含与不包含

| 项目 | 包含 | 不包含 |
|---|---|---|
| 租户 | 一个租户一个商城、共享库 tenant_id、RLS、可信上下文 | 每租户独立实例、集团多店 |
| 身份 | 店主、租户内消费者、内部平台管理身份 | 商户员工、SSO、企业 RBAC |
| 建站 | 一套响应式主题，Logo/名称/色彩配置、平台子域名 | 拖拽装修、自定义域名、主题市场 |
| 商品 | 商品/变体/分类/图片、上下架、单币种定价 | 批量导入、复杂价格表、多语言 |
| 库存配送 | 单仓库、库存调整/预留、固定运费、手动发货 | 多仓、采购、物流 API |
| 交易 | 购物车、服务端计价、简单税率、订单、取消 | 复杂促销、退换货完整流程 |
| 支付 | 一个 Provider、商户独立账户、回调、全额/部分退款 | 多 Provider、代收分账、自动对账 |
| 平台收费 | 单一试点套餐、人工开通/暂停、商品和上传配额 | 自动扣费、按量计费、套餐复杂变更 |
| 运营 | 基础经营统计、审计、监控、限流、异机备份恢复 | 财务总账、租户级 PITR、高级 BI |
| AI | MVP不开发 | 全部AI运营、模型/知识检索/工具平台、经营目标、审批执行与模型评估 |
| 第二阶段客户运营 | MVP不实施此次新增功能或底座 | Helpdesk、双向邮件、客户时间线/身份合并、CRM、营销旅程、完整行为分析 |

只留一个公开交易路径，其余默认模块的 API 不是默认安全开放：不用的入口关闭，有用的入口必须纳入隔离审计。不能只隐藏后台导航。

## 3. 最小数据与技术交付

- tenant、membership、domain、店铺配置、内部平台角色、配额状态。
- 租户归属覆盖商品/价格/客户/购物车/订单/支付/库存/税费/配送及其子记录与 Link。
- 可信 TenantContext、租户内客户身份、服务层守卫、数据库 RLS/索引/唯一约束。
- 租户感知事件、任务重试/补偿、幂等、缓存、锁、搜索和文件。
- 商户支付凭据安全管理，验证回调账户归属与金额。
- 商家后台、固定店面、平台开通管理界面。
- 两租户集成测试、交易 E2E、部署配置、恢复和回滚手册。
- 原生事件、工作流和后台任务仅做租户感知改造；不新增AI指标管道、模型工具、向量检索或审批系统。
- 商家后台优先复用许可允许的原生Admin；消费者店面优先适配现成参考店面，不做全新装修引擎或额外业务模块。

## 4. 开发里程碑

M0–M3 的实际交付见 [基线实施](08-IMPLEMENTATION-PROGRESS.md)、[M1](09-M1-IMPLEMENTATION.md)、[M2](10-M2-IMPLEMENTATION.md)、[M3](11-M3-IMPLEMENTATION.md)。[M4](14-M4-IMPLEMENTATION.md) 已实现 Stripe 独立测试凭据、原生收款/退款、库存履约/取消、签名回调和经营数据。[M5](16-M5-IMPLEMENTATION.md) 已实现平台管理、人工套餐/原子配额、暂停后已付款订单处理、限流/审计/监控/清理和加密备份，并通过本机独立 PostgreSQL 实例恢复。实际 Stripe 沙箱/官方回调/Elements、真实异机备份恢复及 M6 发布门槛仍待完成。下表工时为规划预算，不能当成已消耗工时。

| 里程碑 | 内容 | Codex 工时 | 累计工时 | 验收 |
|---|---|---:|---:|---|
| M0 | MIT 基线、测试环境、归属矩阵和试点 | 24–40h | 24–40h | 许可允许的构建与上下文/RLS 试点通过 |
| M1 | 租户数据、身份、索引、RLS、初始化 | 48–80h | 72–120h | A/B 并发读写拒绝越权 |
| M2 | 全交易隔离、关联、任务和外部存储 | 64–104h | 136–224h | 两店基础交易及负向测试通过 |
| M3 | 后台和固定主题商城 | 80–136h | 216–360h | 两店域名和消费者会话隔离 |
| M4 | 商户支付、库存、履约、退款 | 56–96h | 272–456h | 独立沙箱账户与重复事件测试通过 |
| M5 | 人工套餐、配额、监控、备份 | 40–64h | 312–520h | 暂停不影响退款，异机恢复成功 |
| M6 | 完整验收、性能、安全修复、试点 | 48–80h | 360–600h | 无未解决严重问题，真实支付验收完成 |

顺序体现交易依赖，M3/M5的部分准备可穿插，不据此折减总工作量。M3是现成后台/参考店面的租户适配和必要店铺配置，不是定制重写商城。

**MVP基础预算：360–600h；加约25%余量：450–750h。** 每周40有效会话小时约9–15基础工作周，含余量约12–19周；人工配置/验收参考40–80h，供应商等待另计。AI和客户运营均为第二阶段，不构成MVP依赖或验收门槛。

MVP保留原生交易模块及SaaS必需的tenant/授权、客户账户、业务事件/工作流/任务、基础经营数据、审计和恢复。只维持接口可扩展性，不提前开发AI任务、模型、向量检索、审批、智能报表或客户运营新域底座。

## 5. 必须执行的验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | A/B 使用同一邮箱、handle | 各自正常创建，不共享身份/商品 |
| T02 | A 用 B 的商品/订单/客户 ID 调详情、修改、删除 | 无数据泄漏，无写入；错误策略一致 |
| T03 | A 列表/count、搜索、关系展开、导出 | 不出现 B 数据；结果数量不泄露 B |
| T04 | A 购物车引用 B 的商品、价格、地址或仓库 | 拒绝，且没有部分写入或错误预留 |
| T05 | body/header/域名伪造 tenant_id；A Token 访问 B | 不具备租户授权，不存在默认租户回退 |
| T06 | 无 tenant 的 worker、重启后的 retry/补偿 | 缺上下文拒绝；合法恢复仍属于原租户 |
| T07 | 并发 A/B 请求复用连接池/Provider | 无连接上下文或支付密钥串用 |
| T08 | 重复/乱序支付事件及退款重试 | 不重复扣款、订单、退款或库存动作 |
| T09 | A 请求 B 的文件/缓存内容/导出链接 | 私有对象拒绝；公开文件遵循显式公开规则 |
| T10 | 应用数据库角色直接查询不同租户、raw SQL | RLS 生效；无上下文不返回租户业务数据 |
| T11 | 并发最后一件商品的结账 | 按规则防超卖；失败流程正确释放/补偿 |
| T12 | 暂停 A 租户，B 正常交易 | A 新结账拒绝；A 合法回调和退款继续；B 不受影响 |
| T13 | 并发达到商品数/上传限制 | 配额原子生效，不只靠前端 |
| T14 | 恢复异机全库备份并校验订单/租户数据 | 数据一致、密钥管理可用，恢复步骤可执行 |
| T15 | 10 租户参考负载与 20 并发结账 | 达到 PRD 指标或明确缩小目标，不用端口存活作为验收 |
| T16 | 普通平台人员读取商户业务数据 | 默认拒绝，支持访问须单独授权和审计 |

## 6. 试运营发布条件

1. 选定 MIT 版本与构建产物可复核，商户和平台凭据安全配置。
2. 全部开放入口的 tenant 覆盖矩阵完成，负向测试执行成功。
3. Provider 沙箱与已授权的真实小额支付/退款完成，不能只用 mock。
4. 备份实际恢复、发布回滚、监控报警演练通过。
5. 关键隔离与支付路径独立审查，未解决的跨租户访问、串账和数据损坏问题为零。
6. 先邀请 2–3 家商户，再根据监控扩大到约 10 家试点；租户数量不等于容量承诺。

## 7. 阻塞与降范围规则

- 无商户支付账户：继续独立开发，但真实交易发布保持阻塞，不用模拟 Provider 宣称支付可用。
- MIT 基线不成立：解决版本/授权选择，再继续产品实施。
- 预算不足：先减少主题、装修、角色、促销和报表；不删除隔离、退款或恢复测试。
- 现有生产数据归属不明：先停留在开发测试库，单独制定迁移方案。
- 共用数据库方案出现不可接受改造成本：明确报告和重新决策，不能悄悄改回独立数据库。

## 8. 首个可执行任务

预留 8–16h，计入 M0：核实 MIT 基线、建立数据库环境，选商品与变体做租户隔离试点；验证两个租户同 handle、读写越权、跨租户关联、并发请求与 RLS。提交证据与剩余估算后扩展。

5h 可用于其中一个更小切片，不承诺完成 M0 或基础交易隔离。
