# 第二阶段：AI 原生业务驱动的智能运营 PRD 与实施计划

状态：第二阶段规划，尚未实施。全部AI功能、指标管道、模型/检索/工具、审批和评估都在第一阶段SaaS MVP发布后实施，不构成MVP前置条件。补充并升级原 PRD 的 AI-01；工时替换旧版 E5 基础助手，不与旧版重复相加。

## 1. 产品目标

商户以经营目标驱动运营：例如提高结账转化、减少积压、降低缺货，而不是只能逐条向聊天框下指令。系统持续采集事件、计算可信指标、识别问题、提出行动、经授权执行、观察效果并调整后续计划。

目标 → 事件与指标 → 诊断与证据 → 行动方案 → 策略校验/审批 → 工作流执行 → 效果评估 → 更新策略。

不承诺 AI 自动带来增长。所有经营提升通过对照、样本量和观察窗口验证；不能把订单自然波动当成 AI 贡献。

## 2. 核心产品形态

1. 运营首页：经营目标、今日异常、按优先级排序的机会、待审批行动和执行结果。
2. 智能运营任务：目标、范围、约束、预算、触发器、执行频率、观察窗口、负责人。
3. 行动卡片：数据来源、时间范围、事实/推测、预计影响与不确定性、拟改动差异、成本、风险、执行与撤销条件。
4. 审批中心：批准/拒绝/修改；审批版本与计划绑定，不能审批后再更换价格、收件人或商品集合。
5. 自然语言入口：创建目标、询问指标、检索证据、生成行动；使用同一受控工具体系。
6. 自动化控制：运行中/暂停/限额耗尽、权限和自动执行白名单、总开关、审计、每店费用看板。

## 3. 业务能力与阶段

| 业务域 | 第二阶段AI起步 | 完整 V1 | 边界 |
|---|---|---|---|
| 经营诊断 | 日报、支付失败/订单异常、基础销量与库存提醒 | 漏斗拆解、客群/商品贡献、周期性目标复盘 | 没有事件或成本就不计算对应指标 |
| 商品与内容 | 文案/SEO 草稿、缺图缺描述检查，批准后更新内容 | 商品分类建议、内容任务批次、多语言、关联商品建议 | 不捏造材质/认证/功效，事实字段来自商户数据 |
| 定价与促销 | 只读建议，不执行价格或促销变更 | 毛利约束下的改价、优惠码和活动方案，审批/限额执行 | 缺成本不声称盈利最优；价格边界由规则引擎检查 |
| 库存与补货 | 基于可用库存和历史销量的阈值提醒 | 缺货风险、季节性预测、补货建议、缺货商品活动停止 | 低样本降级；不自动向供应商下采购单 |
| 客户与营销 | 不自动发营销信息 | 客群、生命周期任务、弃购挽回、复购邮件与站内活动 | 授权订阅、退订、频控、禁发群体由服务端执行 |
| 售后与客服 | 内部订单查询与处理建议 | 基于店铺政策的回复草稿、订单异常任务 | 未授权不承诺退款/赔偿，不开放自动退款 |
| 优化与实验 | 记录操作前后指标，不作因果宣称 | A/B 试验、留出组、停止规则和分阶段推广 | 样本不足输出“证据不足”，不自动扩大流量 |
| 渠道投放 | 不包含 | 可生成投放计划和素材草稿 | Google/Meta 等账户连接和自动花费不在本预算 |

## 4. 目标和策略配置

每个目标绑定 tenant_id、owner、指标定义版本、基线、目标值、周期、允许动作、审批规则与预算。

例：减少 30 天未售商品积压，同时维护毛利下限。

- 需要商品、库存、销量、成本和退货数据；缺失字段在行动卡中明确标识。
- 先诊断库存与商品内容，再形成内容改进、曝光和促销候选。
- 若成本未知，改价方案保持建议状态；不估造成本。
- 首次试运行必须人工批准；后续自动执行只限商户明确设置的动作和条件。
- 折扣上限、最低价格、毛利下限、商品范围、频率、总支出均由确定性代码检查。
- 达到预算/错误阈值、数据异常或经营风险条件时停止任务并产生内部提醒。

## 5. 技术架构

Medusa 业务事件 → outbox → 租户事件管道 → 指标聚合/快照 → 规则与分析器 → AI 规划器 → Policy/审批服务 → Tool Gateway → Medusa 工作流 → 结果事件与评估。

关键分工：

- 确定性代码处理金额、税费、库存、毛利、配额、权限、幂等、订阅资格和发送名单。
- 规则引擎先筛选异常、候选商品和动作范围，减少模型成本及错误空间。
- LLM 负责解释、组织计划和文案，不负责直接写数据库或决定授权。
- 时间序列/统计组件处理预测与实验；不把 LLM 叙述当成预测模型。
- 使用有界任务编排，持久化状态和步骤；首版不用无限递归代理或每租户常驻代理进程。
- 模型 API 不可用时，交易系统正常运行；分析任务可排队，关键提醒可用规则降级。

建议数据对象：operating_goal、metric_definition、metric_snapshot、business_event、consent、operating_policy、agent_run、action_plan、approval、tool_execution、experiment、evaluation、ai_usage。除核实后的公共指标字典外均带租户归属与访问约束。

## 6. 数据基础与指标口径

- 采集浏览、商品查看、加购、开始结账、支付成功/失败、退款、发货、库存变动与审批执行事件。
- 服务端交易事件为权威；客户端事件需去重、反机器人和同意管理，不能据此直接变更财务事实。
- 区分下单金额、实收、退款、净销售、毛利、访客/会话、转化率、弃购率。指标含币种、时间区间、时区和分母定义。
- 毛利需要成本和明确费用口径；没有数据不出利润数字。
- 归因窗口、匿名访客与客户关联须明示；隐私配置关闭追踪时降级，不推断不存在的数据。
- 数据源、更新时间、完整性、样本量和 metric_version 写入快照；晚到事件与重算不能重复记账。
- 冷启动采用规则、商户提供目标与阈值；数据不足不输出高置信度预测。
- 数据只属于本租户；默认不跨商户训练、共享记忆或生成跨店基准排行。

## 7. 工具和授权

工具示例：get_sales_metrics、list_inventory_risks、get_product_facts、draft_product_content、preview_content_change、apply_content_change、preview_promotion、apply_approved_promotion、draft_campaign、execute_approved_campaign。

每个工具具有：输入 schema、数据范围、最低角色、风险级别、前置条件、成本估计、幂等键、对象版本、审计字段、补偿或不可逆说明。

tenant 来自可信任务上下文，不接受模型自行选 tenant_id。模型拿不到平台管理员令牌或支付密钥。知识检索、向量数据、缓存、对话历史与报告导出同样租户隔离。

执行时重新检查：当前角色/租户状态、对象归属、规则版本、预算、库存和对象版本、审批有效期。审批过期或业务数据变化必须重新生成预览并审批。

## 8. 自动化等级

| 等级 | 行为 | 默认状态 |
|---|---|---|
| L0 | 只读诊断与报告 | 第二阶段AI起步 可启用 |
| L1 | 草稿/建议，不影响线上 | 第二阶段AI起步 可启用 |
| L2 | 人工批准后执行指定动作 | 第二阶段AI起步 仅商品内容更新 |
| L3 | 商户事先配置规则内有限自动执行 | V1 小范围验证，默认关闭 |
| L4 | 无边界全自动运营、资金操作 | 不提供 |

第二阶段AI起步 不允许自动价格修改、发营销邮件、退款、转账、删店。V1 只在明示授权的白名单中开放有限自动动作；模型提高自己权限无效。

邮件等外部通信必须有商户明确批准的名单/模板或活动策略，并满足消费者订阅、退订和频控要求。生成邮件草稿不等于已获发送授权。预算规划不会实际向任何人发送消息。

## 9. 执行、暂停与补偿

状态机：detected → proposed → awaiting_approval → approved → executing → succeeded/failed/partial → observing → evaluated；另有 rejected/expired/cancelled。

- outbox 与业务事务保证动作结果可追踪；tool_execution 使用幂等键和持久化记录。
- 批量更新分批、保存检查点；重试不重复写入，部分失败逐对象呈现。
- 执行前校验资源版本，防止覆盖商家刚做的修改；不满足即拒绝或重建计划。
- 商品内容变更保存 before/after，可在版本仍匹配时撤回；邮件和已发生支付不能承诺撤回。
- 停止任务阻止后续步骤；已提交外部动作只能检查结果并补偿。暂停租户停止 AI 主动运营，不阻断合法交易回调。
- 总开关、每租户 kill switch、执行次数、模型调用次数和费用上限由服务端控制。

## 10. 成本与资源

- 一种主模型、一个备用/规则降级路径；按任务复杂度路由模型。
- 按租户记录 token、调用、延迟、重试、外部费用与工具结果；请求前预留预算，结束后结算，防并发超限。
- 设租户日/月额度、任务步数、总时长、最大输出和并发；第二阶段AI起步 默认每租户最多 1 个主动运营任务执行。
- 优先聚合指标和检索必要字段，不把全库发给模型；敏感信息脱敏，邮件地址在实际发送工具侧解析。
- 原服务器容量估算不覆盖新增分析与 worker 负载；独立队列优先级/并发，压测时保证支付与结账不被 AI 挤占。
- 模型费用不包含在 Codex 开发工时内。应以 2–3 家试点商户真实任务量核算，不预先承诺固定月成本。

## 11. 评估与验收

参考 第二阶段AI起步 验收目标（待试点校准）：

- 至少 60 个离线案例：20 指标问答、20 商品事实/草稿、20 权限/注入/执行异常。保存输入版本、证据快照、预期和评分。
- 指标数值由确定性工具提供；20 个固定指标案例的金额/计数应与数据库基准完全一致。未知数据明确回答不可计算。
- 所有业务数值、商品事实和行动附可追溯来源；商品草稿的关键事实须逐项对照，不虚构属性。
- 两租户历史、向量检索、工具执行及报告越权测试全部拒绝；没有审批的写操作和预算绕过为零。
- 重复执行、对象版本过期、审批过期、模型超时、任务中断、kill switch、Provider 返回未知状态均有测试。
- 不依靠单次模型运行结论：关键离线集至少重复三次，记录稳定性；任何高影响权限失败为发布阻塞。
- V1 另加营销授权/退订、价格边界、实验统计、低数据预测降级和费用并发预留测试；离线集扩至至少 150 个案例。
- 商业试点记录建议采纳率、实际执行率、每任务费用和人工节省；转化/收入提升通过对照设计观察，不预设保证收益。

独立评审和商户数据反馈仍需负责人协调；模型输出不能作为自身正确性的唯一证明。

## 15. 场景发布顺序

1. AI 日报/诊断与商品草稿 → 人工批准内容更新 → 操作后观察。
2. 商品批次运营与活动方案 → 限定商品的审批后促销。
3. 有订阅授权的客户生命周期营销、库存和售后建议。
4. 具备数据与样本后上线实验评估和有限自动执行。

不从全自动改价/群发/退款起步；上线成熟度由评估证据和商户授权决定，不由聊天界面是否存在决定。
