# 详细基线验证：内容、目标与证据

状态：已开始只读检查；尚未完成完整基线验证。关联 [PRD](01-PRD.md)、[开发计划](02-DEVELOPMENT-PLAN.md)、[AI规格](04-AI-NATIVE-OPERATIONS.md)。

## 1. 本轮目标

确定可合法使用、可重复构建、可完成基础交易的 Medusa 基线；确认共享数据库tenant_id改造的实现入口，形成有证据的继续/调整结论。

区分三种验证：现有功能实际运行、源码/依赖分析、未来改造后的试点测试。现有 Medusa 没有完成租户隔离，不能把源码可修改当成隔离已通过。

## 4. 交易验证细化

至少覆盖商品和变体、同库关联、价格和金额重算、客户/游客、地址、购物车、库存预留、支付授权/收款、订单完成、手动履约、全额/部分退款及失败处理。

使用现有测试/fixture和临时测试应用，默认不改 tracked 文件。确认获许可的代码范围后再执行对应构建与测试。测试数据库和数据必须隔离，不接未知生产库。

系统/模拟Provider用于内部交易回归；外部沙箱验证真实回调、密钥和Provider行为。没有账户时完成内部部分，并把外部部分标为阻塞，不用mock替代通过。真实扣款不是本轮默认动作。

所有结果记录 executed/passed/failed/skipped/blocked/unrun；零测试或服务进程存在不能算通过。确认库变更与任务输出属于本轮执行。

## 5. tenant_id 试点内容

在源码/授权验证后，另做明确的改造试点：Product/Variant及一条跨模块Link，两个租户相同handle，分别CRUD，已知对方ID仍拒绝；同一连接池并发A/B；无tenant、过期上下文和raw SQL；复合约束/RLS/应用账号绕过测试。

当前只读阶段不自动实施这一补丁。试点是在授权与方案成立后的实现任务，不通过设置请求过滤字段伪装完整隔离；试点通过也不代表订单、支付、任务已隔离。

## 6. 当前验证边界

本轮只验证原生Medusa交易和SaaS改造：租户/身份、模块与Link、数据库/RLS、Provider、原生事件/工作流/任务、备份与部署。不验证模型、AI指标平台、向量检索、工具网关、审批执行或智能运营案例，也不要求AI账户。

不为第二阶段提前实施AI或客户运营底座。原生交易事件的tenant传播仍必须验证，这是防跨租户任务与回调的必要工作。

## 7. 顺序与工时

1. B01/B02：先版本和许可；不合适则选定替代基线后重新验证。
2. B03/B04：测试环境、构建和启动。
3. B05/B06：基础交易与异常。
4. B07/B08/B10：表、入口、Provider和共享资源审计。
5. B12：运维与运行基准；B11移至第二阶段。
6. B09：方案验证及有限实现试点，单独记录未覆盖范围。

预计阅读/环境/基线运行及审计16–24h，隔离试点8–16h，共24–40h，计入开发计划W0，不另加项目总预算。支付外部账户等待、MIT基线切换和现有缺陷修复可能要求重估。不能把原先8–16h的第一轮商品验证当成上述全矩阵完成。

## 8. 完成标准与最终报告

- MIT基线：通过、需换版本或授权未决，给出证据与影响。
- 现有电商能力：哪些功能实际执行、哪些失败/阻塞；环境问题与代码问题分开。
- tenant_id可行性：明确改造表、入口、上下文和Provider；试点结果与剩余风险。
- 第二阶段AI和客户运营不构成本轮通过条件，当前报告注明延期范围。
- 交付版本清单、授权矩阵、测试日志、归属/入口矩阵、风险和修正工时。
- 不把现有标准单店交易通过表述为SaaS隔离通过，不把可改造表述为已经实现。

严重许可不确定、核心交易未解释失败、连接池/RLS不可兼容或支付配置串用风险未解决时，不能给出“基线就绪”结论。可先完成不依赖阻塞项的检查。
