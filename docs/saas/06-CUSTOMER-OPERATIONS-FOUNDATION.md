## 1. 范围与架构决策

将电商交易、客服、客户运营、营销和行为统计组成同一租户内的运营系统。自建关键数据、权限和业务界面，渠道基础设施使用外部Provider。默认采用自建简版Helpdesk，不在核心工作台完全依赖外部客服产品；若改为集成现成Helpdesk需另评估同步、许可和租户权限。

默认范围：站内异步工单＋一个支持邮件收发/回调的Provider；电商CRM而非销售线索/商机/合同CRM；单邮件营销；基础行为分析采用已有Analytics适配或外部分析服务，平台掌握事件定义与指标口径。

不包含实时在线聊天/坐席电话、WhatsApp/微信/多社媒、完整CDP、会话录像、广告自动投放或企业销售CRM。邮件发送域名验证、入站支持、沙箱/账户由供应商及负责人配置；当前已有SendGrid通知Provider不代表入站会话已实现。

## 4. 客户身份规则

- 所有Identity包含tenant、provider、external_id、verification状态及Customer/Contact映射。
- 同一邮箱在不同租户是不同客户；不得自动建立跨租户画像。
- 邮件Sender只能作为来源线索，不作为订单权限证明。敏感订单详情须登录/验证或通过受控客服身份访问。
- 访客关联使用受控第一方标识和明确同意；同设备不自动判定同人。不使用IP或单一相似邮箱自动合并客户。
- 合并保留来源、审计和引用迁移规则；可复核错误合并，禁止覆盖原数据而无历史。
- 服务身份能处理来信不等于能查询全部业务数据，工单订单关联也必须tenant一致。

## 5. Helpdesk 第二阶段起步

客户站内提交 → 可信租户/来源校验 → 建工单/会话 → 关联经验证客户与订单 → 店主查看 → AI总结/回复草稿 → 人工确认发送 → Provider反馈 → pending/resolved或重开。

交付：

- 工单状态new/open/pending/resolved/closed、优先级、客户/订单引用、内部备注、消息/附件和检索。
- 一个邮箱收发通道；可信Provider回调/邮箱绑定解析tenant，不能仅相信来信中的tenant_id。
- 外部message_id/thread映射去重；Reply-To及References关联已知会话，未知消息重新校验，不按主题随意合并。
- 入站邮件HTML净化、附件类型/大小限制与安全扫描接入、钓鱼/垃圾内容处理策略、自动回复循环抑制。
- 公开回复和内部备注分离；客户只见其获授权会话，不允许通过工单编号浏览其他人。
- 基础FAQ/店铺政策，AI引用来源生成摘要与草稿；不自动退款、赔偿或发承诺。
- 首版仅店主人工批准回复，不自动向客户发模型生成内容；既有用户任务没有授权任何真实发信。

V1再增加队列、客服角色、指派、SLA营业时间、超时升级、模板宏、知识发布和服务报表。

## 6. CRM、Marketing与行为统计V1

### CRM

租户客户360视图：订单、付款/退款摘要、工单、消息、订阅偏好、获授权行为；标签、固定/动态分群、跟进任务及受控导出。敏感字段按角色限制。营销AI与非AI操作使用同一分群接口。

### Marketing

分群 → 固定名单与同意快照 → 方案/内容 → 商户批准 → 分批调度 → 每次发前重查同意/退订/频控/状态 → Provider回调 → 转化报告。

名单快照不可审批后任意扩张；退订实时生效，可缩小名单。模板、同意、发送和预算都是版本化且幂等的。营销费用上限与模型调用费用分开。只承诺Provider报告的accepted/delivered/bounced等状态，不把邮件打开率当可靠的唯一收益指标。

### 行为统计

web SDK/服务端埋点 → session/匿名身份 → 去重与机器人过滤 → schema验证 → 指标聚合 → 漏斗/来源报告。

支持page_view/product_view/add_to_cart/checkout_start与服务端payment/order事件。对SPA重复导航、同意关闭、晚到/重放事件进行测试。平台决定数据保留期和归因口径；外部分析服务只通过受控查询代理或已验证的隔离项目访问，不能依赖任意tenant属性过滤保护全局Token。

浏览、客服和营销数据都可视为不可信输入；AI不能因消息/网页中出现“忽略权限”而扩大数据访问或执行动作。

## 7. 验收新增项

1. A/B同邮箱、工单号/主题相同不串身份或线程；未知邮件不能跨tenant绑定。
2. 客户A不能读同店客户B工单；公开回复不包含内部备注和不必要支付信息。
3. 重复入站/出站回调不重复工单/消息；断网重试和thread恢复正确。
4. 伪造Provider回调/地址、HTML与附件恶意内容不能绕过控制。
5. 客服询问订单先验客户/tenant/字段权限；来信不是身份认证。
6. 营销未同意/已退订/硬退信抑制客户不发送；审批名单不可扩张；频控和额度并发原子执行。
7. 事件/CRM导出/搜索/向量/知识文章/附件均做tenant和可见性负向测试。
8. 客服AI输出附政策依据，未知政策转人工；注入不能触发退款或泄露其他客户数据。
9. SLA按配置营业时间计时，pending停表/重开规则明确；营销和客服任务不阻塞支付队列。
10. 隐私导出删除覆盖新域数据；依法需保留的财务数据按规则处理，备份保留有说明。

## 8. 开发顺序

tenant/授权 → 客户身份/同意 → 事件/outbox → 双向通信/会话 → 工单/知识 → AI客服工具 → 客户时间线/分群 → 旅程/营销 → 行为统计/归因 → 跨域验收。

与已有W/AM/E/A计划复用接口，不另建多个“当前租户”、事件总线、模型预算或分群规则引擎。交付前新增每张表、每个回调/接口的隔离覆盖项。

## 11. 第二阶段启动验证（非MVP基线门槛）

核对现有Customer/Notification/Analytics/Promotion与上述模型接口；梳理已有对象和规划对象，标注未实现。增加身份合并风险、消息可见性、入站验签、外部服务tenant权限、事件隐私和营销同意的验证项。

第二阶段启动时输出可行性、契约和缺口；无Provider账户、连接器实现时标为未验证，不为了完成基线先发送真实消息或开放消费者数据。
