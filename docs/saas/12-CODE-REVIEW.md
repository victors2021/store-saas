# 已实施代码评审：M0–M3

2026-10-09。评审源为 `/workspace/.medusa-baseline/mit-source` 的 MIT
Medusa 2.18.0 fork，基准 `1014c0337027a6087410ad3cc1da9a11fd83ca8d`。
包含既有模型/迁移、认证、SaaS 网关、原生交易/持久任务/资源边界，以及本次
原生 Admin/参考商城集成。此次是开发过程中的静态复查和回归验证，不代替 M6

## 本批发现与修正

| 问题 | 影响与修正 | 验证 |
|---|---|---|
| 标准 SDK 公钥头被原网关直接拒绝 | `x-publishable-api-key` 与旧自定义头一起逐个校验为当前 Host 的公钥；任何一项指向另一店均拒绝。Host 仍是租户入口依据 | M3 HTTP：本店标准头成功，异店头及混合头失败 |
| Session 使用原始 Host 拼键 | 大小写、端口、DNS 尾点会使同店会话失效。HMAC 命名空间改用已校验的规范化 Host，仍保持不同店独立 | M3 HTTP：同店规范化变体成功；异店 Cookie/JWT 失败；注销失效。M2 重启会话回归 |
| 原始参考商城具有进程级 SDK 身份状态、地区映射和单店缓存假设 | 改为逐请求 Host、逐请求客户凭证；关闭共享响应缓存及租户商品静态生成；缓存失效标签带 Host。公共页面剥离客户凭证，避免错误令牌破坏公共布局 | 双域名重复渲染、同 handle 不同价格、同邮箱独立账号、复制令牌负向浏览器检查 |
| Node 22 内置 fetch 改写自定义 Host | 使用固定后端 URL 时，原店铺 Host 被连接地址替换，导致 SaaS 请求找不到店铺。改用 Node HTTP/HTTPS 显式保存 Host，限制路由、大小和超时 | 真实商城服务端渲染和 Server Action，原生购物车/结账联调 |
| 参考商城子布局覆盖动态 metadataBase | 商品 canonical 被解析为全局 localhost，不能正确标识各店商品。移除子布局的单店 metadataBase，继承请求 Host/可信协议生成的根布局配置 | 浏览器核对双店同 handle 商品的完整 HTTPS canonical，包含实际入口端口 |
| 配送选择仅失效 Next 缓存标签 | 自定义 Node HTTP 请求不登记 fetch 缓存，失效标签不足以保证购物车 props 更新，继续按钮可能停留在旧状态。保存后显式刷新，并等当前选项出现在服务端购物车后允许继续 | 双店真实配送→测试支付流程，按钮启用前验证保存结果；失败时仅记录不含令牌的配送状态 |
| 原生商品列表和 LayoutComposer 都挂载嵌套路由 | 创建商品时出现两个同名表单。SaaS 模式只保留 LayoutComposer 的一个 Outlet | 真实浏览器商品向导创建、发布变体/价格/图片并在店面读取 |
| Express 参数路由抢先匹配库存静态 batch 路径 | `:location_id` 把 `batch` 当作位置 ID，错误套用单条修改 schema。每条路由先匹配已审查的 ID pattern，静态路径进入其正确 handler；库存初始化失败不再显示成功提示 | HTTP 单项库存 batch 创建/异店引用拒绝，原生库存创建与调整浏览器验收 |
| 原生表单默认分页和字段选择超出网关已审查边界 | 有限增加原生页面实际所需字段别名；后台列表上限 1000，公共列表 100。Admin/Store 字段列表分开。先校验 body，再验证对象引用 | M3 HTTP 原生选择器、库存批量与公共敏感字段负向检查；生产构建及类型检查 |
| 新开放写入/关系入口需要更细授权 | 变体必须属于 URL 商品；客户地址必须属于当前客户；库存批量先检查全部商品/仓库/关系，拒绝异店引用与低于已预留数量的修改 | 同店错误父 ID、跨店和同店其他客户地址、混合库存批量无部分写入 |
| 原生分类 DTO 带内部子分类/metadata | 公共分类仅输出启用、非内部记录；隐藏内部/停用子分类、隐藏父分类 ID、metadata 和软删信息 | 原生 HTTP 创建分类后，公共查询及字段扩张负向验证 |
| 上传和原生按钮语义不一致 | 上传按内容签名只接受 PNG/JPEG/WebP；原生表单格式选择同步限制。上传失败停止商品提交，避免无图片仍显示成功。订单/客户中未开放动作隐藏 | 合法图片上传/实际渲染、跨店图片拒绝、SVG 拒绝、原生表单浏览器检查 |
| 浏览器入口新增 Origin/代理风险 | 非安全方法校验完整同源 Origin；同父域店铺同样受限。代理只信任明确 IP/CIDR，保留原 Host、过滤转发头；响应不使用共享缓存 | HTTP 跨源/兄弟域/Fetch Metadata 拒绝、TLS 双 Host Cookie 检查 |

商品选项在 Medusa 2.18 是可复用的多对多关系，不能套用旧版不存在的
`product_option.product_id` 约束。复核保留租户归属和值归属检查，使用原生
options batch 工作流；重复绑定原生拒绝是正确行为。没有为了通过测试放宽原生
关系规则。

## 既有隔离设计复查

- 业务入口由 Host → 活跃租户 → 已验签身份 → 当前成员/客户 → 不透明内部
  上下文建立权限，body/header 不能替代租户授权。平台控制入口和业务入口分开。
- 原生模型、pivot 和物理 Link 的租户列与正式迁移清单一致；运行角色不能拥有
  表、绕过 RLS 或通过角色成员链取得 TRUNCATE 等额外能力。启动检查实际 RLS、
  复合键/FK 和授权，不只信任 migration ledger。
- `SET LOCAL` 和原生查询使用真实事务连接；共享 Provider 是只读目录，不含
  商户密钥。Graph 缓存和未接受的 Index/Redis Workflow 运行路径继续关闭。
- 持久任务绑定 job/tenant/actor/kind/指纹，执行时查当前权限并建立新上下文。
  M2 回归包含独立进程恢复、失败补偿和完成后丢失确认的重放。至少一次交付仍需
  业务幂等，租约续期不延长五分钟的业务授权。
- SQL 缓存、锁、文件元数据和 Session 分区延续 M2；新公开图片路径只接受本店
  明确标记公开的对象。本地文件后端适用于本次单服务器范围。
- 原生模块的全局默认初始化在 SaaS 模式受到限制；M3 业务默认配置只在已验证
  单租户上下文中创建，已有 M2 店铺通过显式、幂等、带审计的命令升级。
