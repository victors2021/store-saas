日期：2026-10-09。复查范围为相对于 M4 `c2f7b1a` 的 M5 增量，以及受到影响
的 M1 网关、M2 任务/文件、M3 前端/启动器和 M4 支付恢复。此为开发过程复查与
故障注入，**独立安全审计仍在 M6**；不能凭本记录宣称所有潜在缺陷已排除。

## 本批修复并验证的问题

| 边界 | 修复与证据 |
|---|---|
| 暂停后的付款判断 | 订单图中的通用 payment_status 不适合作为依据；改查原生 payment collections 和实际 capture 行，只有足额已付订单可履约/发货 |
| 结账与暂停竞态 | 状态动作和交易共用 tenant advisory lock；完成购物车在锁内重新核验状态；已完成订单 replay 保持可恢复 |
| 配额计数 | 商品/文件写入与额度修改共用 usage 行锁；软删、恢复、失败事务及配额降低都由 SQL 验证；追加约束将对象路径绑定当前租户 |
| 上传半失败 | 删除未完成时保留 pending/deleting 记录及额度；文件系统恢复后再清理，避免业务计数低于实际占用 |
| 模式漂移 | 比较真实 CHECK/FK/列/索引/触发器的可移植指纹及特权函数源码，注入删约束/关触发器/改函数证明启动拒绝 |

| 履约恢复参数 | 发货/撤销履约 checkpoint 保存服务器验证的 fulfillment ID；旧缺失 ID 不猜测，交由对账 |
| 原生事件重启 | 签名、负载指纹与当前成员资格验证后，仅匹配明确 event: 命名规则的原生事件允许重新分派；未知命令仍失败，包含大写 Link 事件恢复测试 |
| 清理与恢复 | 只清理完成的原生事件与临时状态；未确认金融操作和全部原生工作流 checkpoint 保留，失败退款重试和已完成恢复通过 |
| 公共流量与退款 | 验证店主使用独立请求预算；消费者触达上限后店主仍能处理退款；回调与认证分别限流 |
| 备份一致性 | 实际业务写入/worker 持共享维护锁，备份持排他锁；客户端断开不能提前释放仍运行的异步变更锁，故障屏障测试验证 |
| 恢复安全 | 认证与 archive/hash 先于建库；拒绝覆盖/路径穿越/符号链接/仓库内密钥导出，包括指向仓库的父目录别名；受限角色 RLS 及跨租户访问在新实例复验 |
| 远程 TLS | 控制连接显式证书校验，避免仅 pg_dump 校验而控制连接弱验证；缺省远程 verify-full，弱模式在访问数据库前拒绝 |
| 前端秘密 | Next 子进程过滤 SaaS 和 Stripe 后端变量；平台 key 只在页面内存，输入清空、退出销毁；生产构建浏览器验证无持久存储 |

采用真实 PostgreSQL、原生 ORM/Workflow、实际 Stripe SDK 和生产前端构建。
退款 500 等故障是有意注入，不通过放宽断言或关 RLS 获得成功。

## 当前设计限制和发布门槛

- 平台 key 是试点运维的共享 bearer 凭据，依赖 HTTPS 和受限入口；细粒度平台
  人员权限、凭据轮换体验和支持访问授权需要另行设计。平台默认无商家订单访问权。
- 配额和分钟窗口是保护措施，不代表商业计费、CPU/内存硬隔离或容量验收。
  店铺交易 advisory lock 仍为粗粒度串行，队列每店一个活动任务。
- 审计完成记录为 best effort；早期限流/维护拒绝不是逐请求审计全覆盖。告警
  当前供 API/控制台读取，没有绑定外部通知通道；M6 配置抓取和演练。
- 对象孤儿扫描为有界本地扫描；大量有效条目之前可能造成后部孤儿延后发现。
  运维需定期完整对象清单核对并评估分页游标；不把有限扫描说成全量回收。
- 金融 ledgers、webhooks、版本凭据和全部原生 workflow checkpoints 不自动删除。
  未建立渠道对账与安全终结准则前，优先保留；需监控增长和磁盘。
- 加密包暂支持 8 GiB，临时明文受文件权限保护，需要受保护的操作盘与足够空间。
  本批没有自动离机传输/定时调度；本地 backup receipt 不代表异机副本。
- 恢复失败会保留已经创建的目标库供调查，程序不 DROP DATABASE。隔离失败目标、
  使用新的空目标重试；任何清理应由运维单独批准。
- 备份恢复不会撤销供应商已发生的金融动作。恢复后、开放写入前须核对 snapshot
  之后的支付/退款与 webhook；签名任务有有效期，超过有效期需审查式重建。
- 实际异机、实际 Stripe、公开部署、安全/许可/CVE、性能和发布回滚尚未验收。
  本次没有外部独立审计或线上生产运行结果。
