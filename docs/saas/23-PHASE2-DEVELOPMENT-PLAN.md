# 第二阶段完整开发计划

更新日期：2026-10-09。状态：规划，尚未实施。本计划汇总既定的电商增强、AI 原生运营、Helpdesk/CRM/营销/行为统计，并新增按租户管理可选模块的工作包。复用 MIT Medusa 2.18.0 SaaS fork、共享应用与 PostgreSQL、`tenant_id` 和 RLS；商家界面继续扩展原生 Admin，不重新建设一套商家后台。

相关规格：[PRD](01-PRD.md)、[原开发计划](02-DEVELOPMENT-PLAN.md)、[AI 运营规格](04-AI-NATIVE-OPERATIONS.md)、[客户运营底座](06-CUSTOMER-OPERATIONS-FOUNDATION.md)。第二阶段范围、顺序和汇总预算以本文件为准；各领域详细规则继续沿用相关规格。

## 1. 目标与启动条件

第二阶段完成一个可商业运营的电商 SaaS V1：平台能管理订阅、模块、团队、域名和数据；商家在原生电商后台使用 AI 诊断、内容、促销、库存和客服能力；客户服务、客户关系、营销和行为统计共享身份、同意、事件和审批体系。

AI 运营形成完整业务流程：经营目标 → 可信指标 → 诊断与证据 → 行动方案 → 规则/审批 → 受控执行 → 效果观察与复盘。模型无法直接获得数据库管理权限或支付密钥，交易不依赖模型在线。

正式启动按既定范围以第一阶段发布验收为前置条件。M0–M6 已有本地开发与验收记录，仍有真实 Stripe 独立沙箱、官方回调/Elements、异机恢复、目标部署与报警、独立审查及商户试点等未完成项；完整状态见 [发布验收](21-RELEASE-ACCEPTANCE.md)。这些剩余工作不算第二阶段新增功能已经完成。

第一阶段预算 360–600h 是历史规划，不是已消耗工时，也不是当前剩余工时。此前提议的平台建店操作界面尚未开工，其 12–20h 估算属于第一阶段体验完善，未计入以下第二阶段预算。

## 3. 模块启用、停用与部署机制

当前 Medusa 具备代码级模块装配、Provider 替换和启动时 `disable` 能力；本 SaaS 的应用模块列表固定，现有 feature flags 不构成通用租户模块管理。共享实例不能因为一个商家停用功能，就卸载其他商家正在使用的模块或删除共享数据表。

实施方式：全局部署经审核的代码模块；租户对可选功能执行启用/停用；平台发布负责实际代码安装、版本升级或移除。AI、Helpdesk、CRM、营销、行为分析适合成为可选功能。商品/购物车/订单/支付/库存及 tenant 隔离等核心能力按依赖固定保留。

| MOD 子任务 | 交付与验收 | 工时 |
|---|---|---:|
| 目录与依赖 | 模块 ID、全局版本、核心/可选标识、依赖、配置契约；启用前检查依赖，禁止错误停用被依赖功能 | 12–20h |
| 租户资格与后端控制 | 租户启用状态、有效套餐、配置、额度；统一校验 API、任务、工具、导出与入口，缓存变更可失效 | 16–28h |
| 生命周期 | 幂等初始化、迁移版本、失败恢复、停用/重启；队列中的未执行动作取消或按规则拒绝，保留历史数据与审计 | 16–28h |
| 管理页面与验证 | 平台模块目录/分配；商家启用状态/设置/依赖说明；两租户不同权限、并发/重试/停用回归 | 20–36h |
| **合计** | **新增范围；不重复实现 E1 计费、E3 角色或 AI 调度** | **64–112h** |

租户启用流程：资格与依赖校验 → 保存启用请求 → 幂等初始化 → 提供可用状态 → 开放界面和 API。停用必须阻止新任务及执行前检查；已提交外部操作先核对状态，合法支付回调/退款处理不能随菜单关闭而丢失。

历史数据按授权可查询/导出，具体保留/删除期限沿用 E4/F6。可选模块停用、租户暂停、套餐欠费为不同状态，明确各自影响和恢复规则。平台升级先做全局兼容迁移，再为租户执行必要初始化；共享表迁移不按租户反复建表。任意上传 npm 插件、动态执行未经审核代码和应用市场不在范围内。

## 5. 按依赖推进的开发顺序

工作包分多批交付时只累计该包一次预算。以下是交付顺序，不是再新增七份工时；独立模块可在接口确定后调整先后，迁移和共用契约统一管理。

| 批次 | 开发任务 | 可验收结果 |
|---|---|---|
| 1 基础契约与模块管理 | MOD；E3 的角色/邀请；F1 的身份/同意契约；AM1 事件/指标；F5 首批采集 | 平台分配可选功能，两租户不同资格；新域模型/权限/事件清单；数据与身份不串店 |
| 2 商业化与店铺能力 | E1 自动订阅；E2 域名/配置；剩余模块初始化接口与状态联动 | 独立计费沙箱、续费/欠费/升级；域名验证、证书、解绑和配置缓存验证 |
| 3 首批 AI 运营 | 完成 A0（AM1–AM5），结合已采集指标和真实商品事实 | 原生后台运营首页、日报/异常、草稿/差异、批准内容更新、暂停/撤回；60 案例 |
| 4 首批客服与 CRM | Helpdesk 起步 HM1–HM4；F1/F2 逐步完成；F3 客户视图；知识和同一邮件适配 | 客户提交工单，店主处理，AI 引用政策生成草稿，人工批准测试回复；客户 360/标签/跟进 |
| 5 营销、分析与商品运营 | F5 报告；A3/F3/F4 分群/受众/旅程；A1 批次商品；E3 促销后推进 A2 | 有同意的生命周期旅程、来源/漏斗、批次内容、受价格边界约束的审批后促销 |
| 6 库存、服务与数据运营 | 完成 E3 多仓/退换货/导入导出、F2 SLA；A4；E4；有样本后 A5 | 库存风险/补货建议、售后处理草稿、SLA、对账/数据恢复、可复核实验报告 |
| 7 完整 V1 验收与试点 | E6/A6/F6；升级/重建/恢复；目标机器压测；商户试点与修复 | 19 个包按实际范围闭环，150 AI 案例与跨域负向测试通过，可审查发布证据 |

行为采集应在同意与身份规则确定后尽早开始，不能等到做预测才发现没有历史数据。A3 营销必须等待 F1 同意/抑制与邮件适配；Helpdesk AI 草稿依赖 A0；A2 依赖 E3 促销和真实成本；A5 等待足够样本。支持专用邮件 Provider 账户、模型账户和部署数据区域需在对应集成前确定，不需要在规划聊天中提交密钥。

## 7. 开发与验收规则

1. 每个工作包先列出现有能力、新增模型/路由/工作流、租户与角色/模块权限、指标/事件契约、失败与恢复策略，再实现；每 8–16 个有效会话小时形成可审查增量。
2. 新业务表、Graph/Link/原始查询、搜索/检索/缓存、文件、报表、回调、导入导出和任务全部补 tenant 约束及负向验证。邮件回调按受信 Provider 配置绑定 tenant，不能相信来信中的 tenant 字段。
3. 模块启停、欠费、暂停、角色变化和额度在执行时重新校验；只隐藏菜单不能通过验收。相同租户不同客户的工单和内部备注也要隔离。
4. 迁移先做兼容扩展、回填与验证，再启用功能；共享 schema 迁移串行验收。回滚不依靠删除历史交易/客户数据；模块停用的数据保留与可查询范围明确。
5. AI 工具执行需要对象归属、角色、版本、审批有效期、费用/业务预算和幂等键。审批后的商品/价格/名单/模板变化必须重新审核；未知外部结果先核对，不盲目重试资金或通信动作。
6. A0 至少 60 案例，关键案例重复三次；完整 AI 至少 150 案例。固定金额/计数与数据库基准一致；事实附来源；越权/未批准写入/预算绕过为发布阻塞。
7. 营销发送逐次校验用途同意、退订、抑制、频控、冻结受众；模型预算与营销费用分别控制。SLA、去重/重试、晚到事件、关闭跟踪、低样本与模型故障都有对应验证。
8. 完整发布具备源码提交、测试/评审记录、迁移与模块状态、运行手册、故障/恢复证据和试点问题闭环。开发自查不替代独立安全审查或真实 Provider/目标环境验收。

## 8. 单机运行与扩容验证

规划参考机器沿用用户确定的 8 核 / 32GB / NVMe。现有 4 核 / 32GB、10 租户、20 RPS/30 分钟的交易 API 测试属于第一阶段证据，不能推断加入 AI、客服和分析后仍具相同租户容量；实际机器及生产数据验收仍待完成。

第二阶段在 E6/A6/F6 内安排混合负载：交易 + 邮件/工单 + 埋点 + 定时分析 + AI 任务。交易回调/结账优先；AI 与行为统计设独立并发、租户日/月预算和队列限额；首批默认每租户最多一个主动运营任务。耗时 AI 工作异步执行，界面显示任务状态，不让下单等待模型结果。

记录各接口 P95/P99、错误率、连接池、队列延迟、数据库/Redis/全机 CPU 与内存、磁盘 I/O、数据增长、模型费用；校验繁忙租户不会挤占其他租户。按 10→25→50→100→200 租户梯度，在足够真实商品/订单/库存/退款/会话历史下测试，达到阈值就停止扩大。目标机器是否支持某个租户数量以测量为准，不预先承诺最大容量或所有请求 300ms 内。

## 10. 本阶段边界与推荐下一步

包含的是电商 SaaS、有限范围自建 Helpdesk、电商客户 CRM、单邮件营销、行为分析与受控 AI 运营。完整 ERP/会计总账、生产/采购/HR、销售商机/合同 CRM、实时全渠道聊天/电话、拖拽建站/主题市场、广告账户连接和自动花费、任意插件市场均需另外立项。AI 不自动转账、退款、下采购单或删除商城。

推荐先关闭第一阶段发布待办，再启动第 1 批：模块目录/依赖与资格、固定角色、客户身份/同意和事件契约。对应功能可在通过验收后逐批发布，无需等 19 个工作包全部完成才交付第一批 AI 或客服能力。
