## 实现范围

| 工作包 | 当前行为 | 范围 |
|---|---|---|
| 商户支付配置 | Owner 在原生 Payments 页面配置独立测试账户；服务端核实账户；凭据加密存储；按版本轮换 | 一账户一租户；轮换保持同一账户；旧支付继续使用旧凭据 |
| Stripe 原生 Provider | 复用冻结的 `@medusajs/payment-stripe` 和 Stripe SDK；每次按可信上下文创建 Provider/SDK | 不共享可变商户单例；仅卡支付、人工全额收款；部分收款拒绝 |
| 商城支付 | 本店支付会话提供自己的 publishable key/client secret，服务端原生计价 | 不使用进程级商城 Stripe 密钥或 Connect 账户；不接受客户端金额、PI ID、metadata 或 capture 设置 |
| 回调 | 原始 body、SDK 签名/时效验证、控制目录定位账户/租户、Host 校验、幂等任务、实时状态复核 | 不信任 body 中的 tenant；不以过时事件覆盖当前状态；关闭会话和取消订单的迟到事件忽略 |
| 交易动作 | 原生工作流完成授权、收款、部分/全额退款、手工履约/发货、取消发货、取消订单 | 一仓库；真实库存预留/扣减/恢复；取消已收款订单由原生流程自动退款 |
| 失败恢复 | 操作账本、Stripe 副作用幂等键、工作流完成凭据、退款/credit-line 恢复标记 | 并发冲突返回 409；API 调用方须保存原键和原 body；不承诺跨数据库/支付渠道的全局 exactly-once |
| 经营数据 | 原生订单数、取消数、Stripe 测试收款/退款/净收款，按币种独立汇总；支付待处理提示 | SQL numeric 汇总；不是财务总账、ERP 或自动结算对账 |
| 启动与升级 | 加法迁移、实际元数据验证、M4 启动器、默认持久 Worker、后台密钥剥离 | 复用网关与私有 Next.js 子进程；不部署公网、不重置正式数据 |

支付配置入口和交易动作只允许本店 Owner。每个租户的客户、购物车、支付会话、
订单、订单项、仓库和发货单均通过已有上下文/RLS及额外归属校验访问。

## 数据与恢复设计

`0006-payments` 增加五张 FORCE RLS 业务表：credential、binding、operation、
effect、webhook；M2 的 134 张受保护表扩展为 139 张。凭据使用 AES-256-GCM，
AAD 包含租户、凭据 ID 和版本；API/签名密钥不进入 DTO、日志或商城子进程。
新增两个服务器控制目录保存不可变账户归属和不透明回调端点，运行角色只获
SELECT/INSERT。端点用复合 FK 关联同店凭据和账户。全局 Provider 目录只保存
`pp_stripe_saas` 的只读定义，不保存商户密钥。

启动核对迁移 checksum 和实际安全元数据，包含五表 RLS/约束/权限、控制目录
权限/唯一键/FK、单店唯一活跃凭据索引和原生订单 change sequence 的最小
USAGE 权限。没有修改 M0–M3 历史迁移文件或放宽运行角色。

操作账本在副作用前持久化，指纹包含种类、资源和请求 body。相同 key 重放，
改变 body 冲突。Stripe 幂等键绑定租户/操作/会话，工作流补偿或重启不改变
它。支付金额更新使用持久 revision，避免金额 A→B→A 重用旧更新的结果。
购物车改价通过原生流程取消并删除旧会话，新会话以重新计算的金额创建。

M4 对六个原生动作工作流启用持久存储和七天 retention 设置；已完成工作流
与接口确认之间崩溃时，重试读取本店完成状态并返回当前 DTO。M2 已禁止全局
无上下文清理；M5 需要协调按租户的清理与未确认操作，不可机械按日期删掉
尚未确认的恢复凭据。退款还覆盖支付步骤已提交、工作流尚未完成的情况：
服务端 operation 标记复用既有原生退款，并避免重复 credit line/transaction。

待结算退款先持久化渠道退款 ID，不提前记录成功；签名退款回调核对渠道最终
金额/币种/会话后完成原操作。渠道后台另行退款或外部部分收款返回
review-required 并显示本店待核对数，保留人工核对入口，不伪造原生财务行。

当前每租户 PostgreSQL advisory lock 串行化结账和订单动作，适用于单服务器
MVP。它不提供租户容量或吞吐承诺；更细锁、队列公平性和压测属于 M5/M6。

## 本批复查 M3 的修正

| 问题 | 修正与验收 |
|---|---|
| 原生后台库存改完后界面可能保留旧值 | 修正库存 levels 列表缓存失效；浏览器检查修改后的 stocked/available 和刷新持久值 |
| 消费者确认页把运费显示为 0 | 使用原生 shipping method amount；两阶段浏览器确认实际 $5 运费 |
| 订单确认页默认写成已经支付 | 区分授权、收款、退款和取消；系统测试支付明确没有资金转移 |
| 原生 Payment 没有逐笔 refunded_amount 的虚拟字段 | 只公开本客户原生 captures/refunds 的 ID 和金额，按真实记录显示退款；不公开 provider 内部数据 |
| 后台扩展未请求 currency/fulfillment 字段 | 在订单扩展显式请求已审查字段，浏览器实际执行收款/退款/发货/取消 |
| 旧会话删除没有独立幂等标识 | 使用服务器绑定的会话 ID；改价、删除及旧回调负向测试 |
| 消费者退出按钮可在 React 处理器就绪前点击 | 等页面就绪才启用，处理时禁用；完整浏览器回归验证退出后重新登录 |

历史 M0–M3 证据保持原样，本次修正和新增验证归档到 `m4-evidence`。

## 仍待验证的外部支付

本环境没有已配置的商户凭据，运行时网络策略尚未开放 Stripe。已提供
`saas/m4-sandbox.cjs`：缺少安全环境输入时返回 `pending`/退出 2，且不触碰
数据库；配置两套独立测试商户账户后可执行真实 test-mode API 的授权、收款、
重复保护和退款。它明确分别记录官方回调和浏览器 Elements 的待验证状态。

必须补齐：两套实际测试账户、正确账户的 publishable/signing key、公网可达的
受审查 TLS 回调入口及 Stripe 官方事件投递、实际 Elements 支付/3DS体验。
本批没有使用 live key 或移动真实资金。正式小额交易仍需后续明确授权及 M6
发布验收。云环境草稿保存不等于网络/凭据已生效，也不等于异机恢复成功。
