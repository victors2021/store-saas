# M6 开发实施与验收

M6 在 MIT Medusa 2.18.0 和 M5 `0007` 数据库结构上继续开发，覆盖入口/RLS
验收、媒体和结账补偿修复、依赖安全更新、监控、安装重建、负载与发布门槛。
本阶段不增加 AI、Helpdesk、CRM、营销或行为分析，不重写商家后台。

本地开发验收与试运营发布分开登记。外部支付、异机恢复、正式部署、独立审查
和商户试点尚需实际证据；开发检查通过不代表可以开放真实商户交易。
完整可复跑步骤见 [M6 README](../../saas/M6-README.md)，发布清单见
[发布验收](21-RELEASE-ACCEPTANCE.md)。

## 本批实现

| 工作包 | 实现与验证边界 |
|---|---|
| 全入口矩阵 | 实际 HTTP 探测全部挂载业务入口的跨店凭据拒绝；TypeScript AST 枚举原生 route 的 HTTP 导出，未纳入允许集的入口实际返回 404；浏览器/签名回调另由 M3–M5 覆盖 |
| 数据库与上下文 | 140 张 FORCE RLS 表的跨租户直接查询、无上下文、运行角色禁止绕过 RLS、160 个交错成功/回滚请求和连接复用检查 |
| 文件安全 | 删除、失败清理、读取和 sweep 校验租户目录真实路径、文件类型/硬链接；危险对象保留记录/占用配额；孤儿扫描使用推进游标和批量查询 |
| 结账补偿 | 同一原生模块事务中仅清理目标租户/订单的软删除 Link 墓碑，保留有效 Link 和支付恢复账；验证跨店和正常订单无法被误删 |
| 并发接入 | HTTP 与后台快照锁连接池分开，保留同一个全局备份门闩；解决并发请求等待后台任务时耗尽同一连接池的问题 |
| 工作流事务边界 | 五个明确的工作流编排入口保留身份/字段/manager 校验，不在整个跨模块流程外占用 SQL 连接；模块 CRUD 和检查点读写继续使用租户事务，12 个跨两店并发购物车更新验证四连接池不饥饿 |
| 目录过滤开销 | 精确的商品渠道 ID 投影/过滤改用运行角色的 tenantSQL，避免每页水合上千个 Link 实体；其他 Query 形状保持原生实现，验证跨店、已有商品 ID 交集和软删除过滤 |
| 多核请求处理 | 两个独立 API 进程共用 DB、对象 namespace 和稳定 keyring，每进程原生/应用池各四连接、一个后台 worker；跨进程会话/购物车即时写入/重复结账/平台撤权及跨店拒绝验证 |
| 不确定退款 | 超过 23 小时且没有远端 ID 的未确认退款，在恢复入口先返回 409，要求人工对账；不会换幂等键再发退款 |
| 可观测性 | 平台认证 Prometheus 指标、静态类别/可信租户标签、序列上限/丢弃计数、TLS 监控 CLI、worker/队列告警与恢复检查 |
| 部署与恢复 | 本地证书校验/错误域名、Host/代理头、Secure Cookie、错身份密钥失败、加密快照/空库恢复/匹配 M6 重新认证；部署模板语法检查 |
| 构建与供应链 | 独立目录 immutable 安装及 74 项无缓存原生重建，原生 Admin/Next 类型、lint、生产构建；完整 lock SBOM/NOTICE/npm 公告及嵌入 native 版本清单 |
| 持续负载 | 十租户目录/订单数据、20 RPS 持续 30 分钟、80/15/5 普通 API、另外 20 并发结账；记录全部延迟/状态、资源采样和队列收敛 |
| 发布门闩 | 十项当前源码/证据摘要/七天有效期/结构化事实校验；生产启动在任何未完成项存在时拒绝，不自动迁移、支付或部署 |

## 严格验证结果

最终执行结果以 [M6 证据汇总](m6-evidence/summary.json) 为准；详细日志与 JSON
分别记录构建、M0–M5 回归、M6 新增检查、供应链和性能。开发过程中发现的失败
候选没有计入最终通过数。

首次全数据负载曾出现 Knex 连接池超时，独立复现定位到工作流外层事务占满
四连接池并等待自己的业务步骤。修复后重新执行完整验收；保留失败诊断和
修复前后对照，不将首次失败或小数据 smoke 计为 30 分钟通过。

另一次候选中的“缺上下文编排拒绝”断言未捕获同步拒绝，修正断言后续跑；
随后完整数据又暴露目录过滤的 CPU/排队开销。该候选的 12 分钟诊断 P95 约
12.5 秒并有背压，明确不计入通过。目录过滤优化后的一分钟诊断全部 1,200
请求成功，整体 P95 仍约 2.6 秒，最后 20 秒约 653ms，仅用来定位启动/稳定态。
随后单进程完整普通负载记录 36,000 次请求，P95 约 **8,771ms**，包含 119 个
409 和 6 个背压记录；即时结束 worker 时还有一条待处理普通事件。该候选
`complete=false`，不计入通过。部分单进程测量与独立小型回归重叠，因此仅作
失败诊断，不作为严格隔离的 A/B 百分比对照。普通事件改为在真实 worker 运行
时最多等待 60 秒收敛，再检查队列；等待时间另行记录，不改变 API 延迟统计。

双进程完整数据的 **120 秒诊断**共 2,400 请求全部 200，整体 P95 **228ms**、
最后一分钟 P95 **187ms**。其中商品浏览 P95 147ms、购物车读取 79ms、购物车
写入 353ms、订单读取 150ms。诊断没有后台 worker，不代替最终持续负载或
“所有接口≤300ms”的保证。最终源码重新执行整条严格脚本和完整 30 分钟负载；
失败候选、断言失败与 CPU 诊断均单列保留，不将短时诊断当作完整验收。

新增安全检查包含 165 个挂载业务入口探测、332 个关闭的原生方法/路径探测，
以及全部 140 张 FORCE RLS 表、混合连接上下文和媒体删除/sweep。路径探测使用
不存在的合法 ID，验证的是授权/路由边界；具体实体的跨店字段、写入、关联、
回调、退款与浏览器行为由各阶段更细的业务回归验证。

20 个同时结账以剩余两件库存为冲突目标，初始请求允许成功或可重试 409，随后
按原键恢复。最终只能新增两个有效订单；失败流程无失联订单、失败补偿步骤、
错误预留和负库存。缺库存任务经过有限重试达到终态失败，保留检查记录。
这种 409 是并发接入/队列恢复协议，不是“20 个请求全部即时成功”的承诺。

## 性能结果的解释

最终数值见 [performance.json](m6-evidence/performance.json)。默认数据为 10
租户、合计 10,000 商品/20,000 变体/100,000 订单；浏览/购物车/订单读取共
36,000 次请求。结账冲突单列，供应商等待单列为未实测。

按用户追加目标，当前普通 API 整体 P95 阈值为 **≤300ms**，替代原规划的
800ms；全部测量请求及初始冷请求均计入。双进程负载分配使商品列表/详情和
订单列表/详情都经过两个进程，报告按进程、租户、业务和读写操作分别统计，
同时采样两进程 RSS/CPU 和整体 API RSS。发布模板提供两个独立网关/Next 端口
及分开采集的进程指标；没有引入跨请求业务缓存。负载请求直接访问 API，
不包含公网/TLS/Nginx/Next 渲染的完整页面等待，不能保证每一个写接口都低于
300ms。最终是否达到该整体目标以完整报告的 `performance.passed` 为准。

当前 cloud 可见 5 CPU，cgroup 配额 **4 核**、内存上限 **32 GiB**，不同于
PRD 的 8 核/32GB 参考机。历史订单使用原生工作流模板在 RLS 下批量克隆，
覆盖订单/地址/行项目/汇总/配送，未制造完整历史支付、退款、履约和工作流账。
批量目录保留价格/渠道/配送关联，但克隆变体不管理库存；实际共 10 个原始受管
变体/库存项和 19,990 个未受管变体。另行结账冲突在原始库存项上验证，不能
等同 20,000 个受管 SKU、多仓库和完整历史库存账的生产负载。见只读记录
[目录数据配置](m6-evidence/catalog-profile-verification.json)。
还存在单独的闲置开发后台进程。结果只能描述本环境和该负载，不能推导可售
租户数量，也不能宣称完整真实支付负载或参考服务器容量已获确认。

性能报告分别记录普通流量结束和结账冲突后的队列；普通事件需无失败收敛，
缺库存结账允许有限终态失败但不能无限 pending/running。进程 RSS/heap、整体
cgroup 内存与 CPU 使用有采样；目标机仍需独立审查增长、真实 DB/缓存/代理和
供应商延迟，以及真实目录的受管库存/多仓和历史数据构成。
当前 `releaseQualified=false` 保持明确。


最终双进程完整结果：**36,000 次请求全部 HTTP 200，整体 P95 207.9ms**，达到当前普通 API 整体 300ms 目标。

| 操作 | 请求数 | P50（ms） | P95（ms） | P99（ms） |
|---|---:|---:|---:|---:|
| 全部普通 API | 36,000 | 71.1 | 207.9 | 325.7 |
| 商品浏览 | 28,800 | 70.7 | 142.2 | 194.1 |
| 购物车读取 | 3,600 | 53.4 | 81.7 | 105.3 |
| 购物车写入 | 1,800 | 260.3 | 379.2 | 475.1 |
| 订单读取 | 1,800 | 92.8 | 146.9 | 177.6 |

每进程各处理 18,000 个请求；普通队列于负载结束后 52ms 内收敛。20 并发结账在剩余两件库存下最终只新增两单，
无超卖或失联订单，缺库存任务有限重试后到达终态。购物车写入 P95 仍高于
300ms，整体达标不等于每个接口达标。全部 API 进程 RSS 峰值约 1.43GiB；
不包含其他进程的 RSS，整体 cgroup 内存另有采样。

## 安全依赖升级与许可

首次官方 npm bulk 扫描观察到 235 条公告；本批兼容更新后观察到 39 条，
包括 critical 2/high 8/moderate 19/low 10。数字按公告计，不按实际可利用漏洞计；
最终时间、准确 lock 摘要和组件数以供应链证据为准。

更新包括 Next/eslint-config-next 15.5.27、axios 1.20.0、morgan 1.12.1、
multer 2.4.0、proxy-addr 2.0.8、qs 6.16.0、form-data 4.0.6、ws 8.21.0、
compression 1.8.2、handlebars 4.7.10、tar 7.5.22、兼容主版本下的 URI/
glob/YAML/CSS/build 依赖。Vitest 3.2.6 修复 UI 严重公告；其 Tinypool 1.x
仍有两条 critical，没有兼容主版本修复，未用一次盲目大版本替换宣称清零。
更多上下游关系/评估见 [开发复查](20-M6-CODE-REVIEW.md)。

根 MIT LICENSE、原生模块 2.18.0 版本和已应用迁移保持原哈希；M6 明确改变
根 manifest/lock、商城 manifest/lock 和根 `.yarnrc.yml`，最后一个将 checksum
默认值改为 `throw`。历史报告“根 manifest/lock 冻结不变”描述的是 M0–M5，
不能继续作为当前依赖升级后的断言。

SBOM 覆盖两份锁的完整边和可选包，另记录 sharp/libvips 的 28 个嵌入库版本。
NOTICE 包含当前安装依赖的许可正文，未安装可选包及缺元数据仍待审查。
Native bundle 声明 LGPL，实际镜像/二进制分发、对应源/许可通知义务和 OS/基础
镜像漏洞需另审，Medusa MIT 不会将这些依赖改许可。

## 用户追加的管理员设置

已按用户指令登记独立持久开发库中的平台管理员 `platform_admin`，保存稳定
本地开发密钥并实际登录平台运营界面。该库为 `medusa_saas_preview`，不属于
可重置测试 fixture。截图见 [平台管理员登录](m6-evidence/platform-admin-login.png)。
平台仍采用密钥登录，商家 Admin 使用租户内邮箱/密码。所有私密运行 keyring、
平台 key 和 TLS 私钥在 Git checkout 外权限受限保存；正式 Secrets 和公网入口
没有由此设置。开发平台仅监听 loopback，用户访问须配置转发与域名映射。

## 保留的外部验收

按用户决定，真实异机备份与恢复列入发布验收；本地独立 PG 和恢复演练不能
代替异机验证。实际独立 Stripe 沙箱/官方 HTTPS 回调/Elements 3DS、已授权小额
支付退款、正式 TLS 入口/报警送达/回滚、独立审查、真实商户走查均需要证据。
本批开发验收不自动发送通知、扣款、覆盖未知数据库或公开部署。

M0–M5 已登记的 268 份历史证据保持原字节/摘要；M6 单独保存增量与累计源码
补丁、源码清单和证据 SHA256。安装重建为同一物理主机的新目录和现有包缓存，
不是“新云任务已恢复验证”。云配置保存为复用草稿，需要在环境设置保存/发布
后再验证；推送源码、保存草稿和应用发布是三个分别确认的状态。
